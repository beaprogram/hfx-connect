### Design

Full rationale in
[ADR-014](../decisions/ADR-014-saved-resources-design.md). The
questions with real design weight: a focused entity vs. a generic
bookmark framework (chose focused — nothing else is saved today);
whether the relation should die with a deactivated resource (chose
no — it's excluded from the list but preserved, reappearing if the
resource is reactivated); and how the frontend keeps a private,
per-account cache correctly isolated across logout and account
switches within one browser tab (resolved by having `AuthProvider`
itself clear every `saved-resources`-rooted TanStack Query on both
events, since it already owns the moment those events happen).

**A real bug was found during this pass, not by either automated test
suite**: the very first save attempt from the browser failed with a
CORS preflight error (`No 'Access-Control-Allow-Origin' header`) on the
`PUT` request specifically, while the `GET` status/list requests worked
fine moments earlier on the same page. Traced to
`WebCorsConfig.corsConfigurationSource()`'s `allowedMethods` listing
only `GET`/`POST` — a gap that had existed since this bean was first
written (Milestone 5C) but was invisible until this milestone's
save/remove endpoints became the first browser-driven `PUT`/`DELETE`
calls this codebase has ever made (the existing admin `PUT` routes on
`ResourceController` were previously only ever exercised by backend
integration tests, which call the API directly and never go through a
browser's CORS layer at all). Fixed by adding `PUT`/`DELETE` to the
allowlist and adding a new
`CorsConfigurationIntegrationTest.preflightAllowsPutAndDeleteForTheSavedResourcesRoutes`
regression test before re-running the full manual pass (27/27 green)
and the full backend suite (554/554, the new CORS test included).
