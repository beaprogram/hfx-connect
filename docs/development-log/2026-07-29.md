### Design

Wrote [ADR-011](../decisions/ADR-011-operating-hours-and-open-now.md)
before implementing: `America/Halifax` fixed and server-authoritative
(Halifax observes DST, so a raw offset would be wrong half the year);
`Clock` injected everywhere a calculation needs "now," never
`Instant.now()`/`LocalTime.now()` inline; `opensAt > closesAt` means
"crosses midnight," `opensAt == closesAt` rejected rather than treated as
an implicit 24-hour day; `UNKNOWN` only when a resource's schedule is
entirely absent, so `openNow=true` has one unambiguous meaning; the
existing ADR-010 unified query extended with two more predicates plus a
correlated `EXISTS` subquery for `openNow`, rather than a new query layer
or a `Specification` rewrite; batch-loading (`findByResourceIdIn`) for the
list path rather than a collection fetch-join.

### A Wire-Format Assumption Worth Verifying, Not Assuming

The milestone brief's own example suggested `opensAt`/`closesAt` would
serialize as `"09:00"` (`LocalTime#toString()`'s zero-seconds-omitted
form). Rather than writing the frontend Zod schemas and `formatLocalTime`
against that assumption, added a real backend test
(`ResourceApiIntegrationTest#operatingHoursTimesSerializeAsIsoLocalTimeWithSeconds`)
that PUTs a schedule and asserts on the raw JSON body — confirmed the
actual wire format is `"09:00:00"` (Jackson's default JSR-310
`LocalTime` serializer always uses `DateTimeFormatter.ISO_LOCAL_TIME`,
which is not the same formatter `toString()` uses). The frontend was
written against this verified format from the start, and the test now
exists as a permanent regression guard against a future Jackson/config
change silently breaking every frontend consumer of this field.
