### A Pre-Existing Flaky Test, Found Before Any New Code

Running the baseline suite at 00:47 AM local time surfaced a real,
pre-existing bug unrelated to this milestone: four
`ResourceServiceIntegrationTest` tests and one
`ResourceApiIntegrationTest` helper built an "open now" schedule window
as "now-1h to now+1h, tagged with today's real day-of-week" — which
breaks specifically within the first hour after midnight, when
`now-1h` rolls back into the previous calendar day while the entry
still claims to be "today," producing an overnight interval that
doesn't actually cover the real current moment. The production
`OpenNowCalculator` was never affected — it already derives each
entry's day independently. Fixed by deriving the entry's day-of-week
from the window's own start instant instead of "today," committed as
its own fix before any Milestone 8B code was written.

### Pre-Implementation Review

Read `User`/`CurrentUserPrincipal`, `CommunityResource`, `Category`,
`ResourceValidation`, `SecurityConfig`'s route matrix, and
`SavedResourceService`/`SavedResourceRepository` (Milestone 8A) as the
closest precedent for a private, owner-scoped, paginated domain.
Decided on `UUID` primary keys for both new tables (not `BIGINT`
identity like `saved_resources`) since a submission/report genuinely
is addressable by its own id in a URL, with no natural-key alternative
— the same reasoning `resources.id`/`users.id` already established,
correctly re-applied rather than defaulting to the most recent
precedent. Widened `ResourceValidation`'s field-level helpers (and
`CategoryNotFoundException`/`InactiveCategoryException`) to
`public`/`public static` for cross-package reuse, the same pattern
`ResourceNotFoundException.byId` established in Milestone 8A.

### Design

Full rationale in
[ADR-015](../decisions/ADR-015-community-contribution-workflows-design.md).
The genuinely hard design questions: two focused tables vs. one
generic contribution table (chose two — the shapes are real different,
and a discriminator column would just hide that); three different
foreign-key deletion policies across two tables and three columns
(`RESTRICT` on both owning-account columns, since contribution history
has standalone value even after account deletion — the opposite of
`saved_resources.user_id`'s `CASCADE`; `SET NULL` on the correction
report's target-resource column, with a name/slug snapshot captured at
creation, since a report about a since-deleted resource still has
review value); and the duplicate-pending guard, expressed as a
PostgreSQL partial unique index scoped to `WHERE status =
'PENDING_REVIEW'` so a withdrawn/resolved item never blocks a later
resubmission.

### A Real Bug Found During Service-Layer Testing

A test chaining "withdraw a submission" immediately followed by
"resubmit the identical name/category" failed with an unexpected
duplicate-pending conflict, even though the withdrawal had already run
first in program order. Root cause: Hibernate's flush action queue
processes entity insertions before updates within a single flush,
regardless of call order — so the resubmission's `INSERT` could
physically reach the database before the withdrawal's `UPDATE` did,
within one shared session. Fixed by having `withdraw()` call
`saveAndFlush` explicitly rather than relying on implicit auto-flush
timing, documented in `docs/architecture/backend-architecture.md`'s new
"Flush Ordering Within a Single Transaction Is Not Call Order" section.
