### Design

Wrote [ADR-009](../decisions/ADR-009-request-authentication-and-role-authorization.md)
before implementing: `spring-boot-starter-security` added for the first
time (Milestones 5A/5B deliberately avoided it); every authenticated request

two-rule policy; `ORGANIZATION` excluded from resource creation until

### A Jackson-Version Wiring Bug, Found Immediately at Startup

The first attempt at `ApiAuthenticationEntryPoint`/`ApiAccessDeniedHandler`
autowired `com.fasterxml.jackson.databind.ObjectMapper` (the obvious,
familiar type) to serialize `ApiError`. The application context failed to
start: `NoSuchBeanDefinitionException` — no Spring bean of that type exists,
because this project's actual Jackson runtime stack (confirmed via
`dependency:tree` during pre-implementation review, not assumed) is Jackson
3.x (`tools.jackson.databind`), and Spring Boot 4.1's auto-configuration
registers its `ObjectMapper` bean under that package, not the legacy
`com.fasterxml.jackson.databind` one (which is present on the classpath only
transitively, via JJWT's own bundled Jackson 2.x, and never becomes a Spring
bean). Fixed by importing `tools.jackson.databind.ObjectMapper` instead —
caught in the very first `./mvnw test` run, before any commit, exactly the
kind of version-specific surprise `frontend/AGENTS.md`'s warning (about a
different but analogous risk) exists to guard against on the backend too.

### Existing Tests Broken by the New Authorization Requirement — Fixed, Not Weakened

Adding `POST /api/v1/categories`/`resources` authorization broke
`CategoryApiIntegrationTest`/`ResourceApiIntegrationTest` (they'd previously
posted with no token at all) and `GlobalExceptionHandlerIntegrationTest`
(an unauthenticated request to a genuinely unmapped path is now rejected
`401` by `SecurityConfig`'s `anyRequest().authenticated()` default before
Spring MVC's own routing — and 404 — is ever reached). Fixed by issuing a
real `ADMIN` Bearer token per test class (`TestUserFactory`, built via
`User`'s existing package-private full constructor) rather than loosening
the new requirement, and by re-pointing the unmapped-route 404 assertions at
an authenticated request (adding a new, explicit test locking in the 401
behavior for the unauthenticated case instead).

### A Pre-Existing, Order-Dependent Test Assumption, Exposed by New Tests

`ResourceServiceIntegrationTest` had three assertions of the form
`resourceRepository.count()).isZero()` after a rejected creation — an
assumption that only ever held because of incidental Surefire test-class
ordering against this project's shared Testcontainers singleton database
(each test method's own `@Transactional` rollback undoes only what that
method itself wrote, not rows other, non-transactional HTTP-layer test
classes already committed earlier in the same run). Adding
`AuthorizationMatrixApiIntegrationTest` (which legitimately creates real
category/resource rows) perturbed the ordering enough to break this
assumption. Fixed by comparing a captured before/after count instead of
assuming a globally empty table — a genuine isolation improvement, not a
workaround.
