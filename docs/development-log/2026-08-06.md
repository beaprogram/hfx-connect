### Design

Full rationale in
[ADR-016](../decisions/ADR-016-moderation-workflow-design.md). The
genuinely hard decisions: row-level `PESSIMISTIC_WRITE` locking over
`@Version` for concurrency control (makes the whole review transaction
authoritative, not just the final `UPDATE`); locking the *target
resource* row separately from the *report* row for correction
application (two different pending reports can target the same
resource — a lock on the report row alone wouldn't prevent a
lost-update race between them); an audit model where
`RESOURCE_CREATED`/`RESOURCE_UPDATED`/`RESOURCE_DEACTIVATED` rows carry
their own decision/reason/actor directly, and a bare `REVIEW_DECISION`
row exists only when a decision has no such effect to attach to; and
which of `CorrectionReport`'s actual V9 fields this workflow could
honestly apply automatically (13 scalar fields — never category, never
`OPERATING_HOURS`/`DUPLICATE_RESOURCE`, since neither has real
structured data to apply).

### A Real Defect Found During Manual Verification, Not by Any Automated Test

`CommunityResource.lastVerifiedAt` was added and correctly threaded
through the entity, `ResourceService.createVerified`, and the
moderation-facing audit snapshots — all of which compiled and passed
every test written against them. It never reached the *public*
`ResourceResponse` DTO (`GET /api/v1/resources/{id}` and
`.../slug/{slug}`), because no automated test asserted that DTO's
actual field set end-to-end against a live response. Caught only by
curling a real approved resource during the manual verification pass
and reading the response body directly. Fixed (`ResourceDetails` and
`ResourceResponse` both updated), the backend dev server restarted, the
full manual script re-run clean, and a permanent regression test added
(`ModerationResourceSubmissionApiIntegrationTest
.publishedResourceExposesVerificationStatusAndLastVerifiedAtPublicly`)
so this specific gap cannot silently reopen. Documented as a general
lesson — not specific to this one field — in
`docs/architecture/backend-architecture.md` and ADR-016: an
entity/service-layer change passing every test written against that
layer does not imply a sibling response DTO exposing the same
underlying data was actually updated too.
