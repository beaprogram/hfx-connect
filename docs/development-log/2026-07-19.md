## Technical Decisions

- Used `saveAndFlush()`, not `save()`, in `ResourceService.create()`'s
  try/catch around the insert. `CommunityResource.id` is a Hibernate-generated `UUID`
  (assigned in memory, no forced synchronous `INSERT` the way `Category`'s
  `GenerationType.IDENTITY` requires), so a plain `save()` is not guaranteed to hit the
  database inside the try block — the race-condition catch would have been unreliable.
  Documented in a code comment and in `docs/architecture/backend-architecture.md` so a
  future "simplification" back to `save()` doesn't silently reintroduce the bug.
- Typed `CreateResourceCommand.costType`/`UpdateResourceCommand.costType` as the
  `CostType` enum directly, not a `String`. Possible only because there is no HTTP JSON
  boundary in this milestone; Milestone 3C's HTTP DTOs will need their own
  string-to-enum parsing and invalid-value handling, which is correctly that
  milestone's concern, not this one's.
- Did not create a new ADR for the UUID-vs-BIGINT resource identifier decision — it's
  already fully covered by ADR-005, which explicitly anticipated resources using UUID
  when categories' BIGINT key was decided in Milestone 3A. Updated ADR-005's
  Consequences section (file-path reference) instead of duplicating its reasoning in a
  new document.
- `ResourceServiceIntegrationTest` uses real `CategoryRepository`/`ResourceRepository`
  instances (Testcontainers), not Mockito, unlike `CategoryServiceTest`. This was an
  explicit instruction for this milestone, and it's the right call regardless:
  `ResourceService`'s most important rules (category existence/active-state checks)
  are precisely the kind of cross-entity behavior a mock cannot meaningfully prove.

## Problems Encountered

1. Colima was not running at the start of this session (stopped since the last one) —
   the database container itself was preserved and came back healthy once Colima
   restarted.
2. `ResourceRepositoryIntegrationTest.deletingAReferencedCategoryIsRejected` initially
   failed with `InvalidDataAccessApiUsageException`/`TransientPropertyValueException`
   instead of the expected `DataIntegrityViolationException`. Deleting the same
   in-memory `Category` instance a still-managed `CommunityResource` already
   referenced confused Hibernate's own in-memory consistency check before any SQL was
   sent, masking the real `ON DELETE RESTRICT` behavior under test.
3. `GET /api/v1/resources` returned `500` instead of `404` (see Work Completed) — a
   genuine, pre-existing, general-purpose bug, not a resource-domain defect.

## Resolution

1. No action needed beyond restarting Colima; the named volume was untouched.
2. Detached the persistence context (`entityManager.flush()`/`.clear()`) and
   re-fetched the category fresh before attempting the delete, so the test observes
   PostgreSQL's actual rejection of the `DELETE` statement rather than Hibernate's
   in-memory pre-check.
3. Added `@ExceptionHandler(NoResourceFoundException.class)` returning `404 NOT_FOUND`
   to `GlobalExceptionHandler`, ahead of the generic `Exception` handler; added a
   regression test.
