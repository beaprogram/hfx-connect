### Jest Configuration Bug (Real, Pre-Existing)

### Disk Space Environment Problem

Partway through implementation, `npm test`, `tsc --noEmit`, and eventually
even `cat` of small tracked files began hanging indefinitely. `df -h`
showed the internal disk within ~1.6GB of its 228GB capacity. Diagnosed via:
elimination (confirmed `/tmp` reads/writes stayed fast, isolating the
problem to the project's own disk location), `lsof`/`sample` on a hung
`jest` process (showed near-zero CPU accumulation over minutes — genuinely
blocked, not computing), and reproducing the same hang with `tsc --noEmit`
(ruling out a Jest-specific bug).

Flagged this to the project owner rather than attempting to free disk space
unilaterally (freeing space safely requires knowing what's safe to delete
outside this project, which isn't this session's call to make). Owner
connected an external SSD (`/Volumes/PortableSSD`, 861GB free) and asked
for the project to be transferred there and the original freed afterward.

Transfer approach (first attempt — a single `rsync` of everything including
`node_modules`/`.git` — was abandoned after ~20 minutes at only ~680 files
copied, confirming the degraded disk made a full recursive copy
impractically slow):

1. `rsync` of source files only (excluding `node_modules`, `.next`,
   `coverage`, `target`, `.git`) — 194 files, ~1.2MB, completed in seconds.
2. Separate `rsync` of `.git` (536KB, 461 loose objects) — needed two
   passes (the first appeared to finish per its process exit but left the
   destination with only 67/461 objects; a second, identical `rsync`
   invocation copied the rest) — verified with `git fsck --full` (clean)
   and `git status`/`git log` on the SSD copy afterward.
3. One more incremental source-only `rsync` to catch up files written
   between steps 1 and later implementation work.
4. `diff -rq` (excluding the same build-artifact directories) between the
   original and the SSD copy — confirmed the SSD copy was a strict superset
   (newer content only, nothing missing) before treating it as canonical.
5. Fresh `npm install` (678 packages in 5 seconds — versus indefinite
   hangs on the original disk, confirming the root cause was disk I/O, not
   this project's dependencies or configuration) and `./mvnw` (regenerates
   `target/` from scratch) on the SSD copy.

### Defects Found and Fixed Before Commit

Two real test-authoring bugs were caught while running the suite, both fixed
before this work was considered complete:

- `UserRepositoryIntegrationTest`'s uniqueness-constraint test initially used
  `userRepository.save(...)`, which does not force a synchronous `INSERT` for a
  Hibernate-generated `UUID` primary key (the same reasoning
  `docs/architecture/backend-architecture.md`'s `saveAndFlush` section already
  documents for `ResourceService`) — the constraint violation was never thrown
  inside the test's `assertThatThrownBy`. Fixed by switching the test helper to
  `saveAndFlush`.
- `UserApiIntegrationTest.registerResponseBodyNeverContainsAPasswordField` used
  an email address literally containing the word "password" as a uniqueness
  suffix, causing its own `doesNotContain("password")` assertion to fail
  against the response body's own `email` field — a test-data naming mistake,
  not a real leak. Renamed the test's email prefix to remove the false
  positive.

Also fixed a now-stale hardcoded assertion in the pre-existing
`FlywayMigrationIntegrationTest` (`containsExactly("1", "2", "3")`), the same
category of fix Milestone 3A already made once for the same test file — updated
to `"1", "2", "3", "4"` now that a fourth migration exists.

### Environment Notes

Two Colima-specific issues were hit while running `./mvnw clean verify`,
neither a code defect:

- Testcontainers could not find a Docker environment at all until `DOCKER_HOST`
  was pointed at Colima's socket (`unix://$HOME/.colima/default/docker.sock`) —
  already documented in `backend/README.md`'s Troubleshooting section from a
  prior milestone.
- Once that was set, Testcontainers' Ryuk resource-reaper sidecar itself failed
  to start (`Container startup failed for image testcontainers/ryuk:0.14.0`) —
  not previously documented. Resolved with `TESTCONTAINERS_RYUK_DISABLED=true`,
  safe for this project's shared-singleton-container test setup since cleanup
  already relies on the JVM exiting, not specifically on Ryuk. Added to
  `backend/README.md`'s Troubleshooting section.

Manual verification against the real docker-compose database hit the
already-documented port-5432 conflict (a native Homebrew PostgreSQL install on
this machine, confirmed via `lsof -nP -iTCP:5432 -sTCP:LISTEN`, was intercepting
the connection — surfacing as `role "hfx_connect" does not exist` even though
the role genuinely exists in the Docker container). Resolved with the
already-documented `POSTGRES_PORT=55432`/`DB_PORT=55432` override, not a new
finding.
