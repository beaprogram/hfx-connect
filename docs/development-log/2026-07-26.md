before implementing: short-lived signed JWT access token (JJWT 0.12.6, HS256)

### A Real Transaction-Management Bug, Found and Fixed

`RefreshSessionService.rotate()`'s reuse-detection and account-unavailable
branches both revoke a session (or a whole rotation family) and then throw —
a write that must survive the exception. The first implementation used
`@Transactional(noRollbackFor = {RefreshTokenReusedException.class, AccountUnavailableException.class})`.
**Automated tests (mocked) passed, but a live reproduction did not:** logged
in via `curl`, refreshed, then presented the original (now-rotated-away)
cookie again — the API correctly returned `401 REFRESH_TOKEN_REUSED`, but a
`psql` inspection of `refresh_sessions` immediately afterward showed the
sibling (rotated) session still `revoked_at IS NULL` — the bulk revoke had
executed (confirmed by temporarily logging its returned row count: `1`, as
expected) but had not persisted. Root cause not fully diagnosed within this
milestone's scope; `noRollbackFor` was simply not trusted further. Fixed with
explicit, programmatic transaction control — a `TransactionTemplate`
configured with `PROPAGATION_REQUIRES_NEW` — and re-verified with the exact
same live `curl`+`psql` reproduction before considering it resolved. See
ADR-008's implementation note and `docs/architecture/backend-architecture.md`'s
new section on this discovery. This was only catchable through genuine
full-stack manual verification — the mocked `RefreshSessionServiceTest` cannot
exercise real Spring transaction demarcation at all.
