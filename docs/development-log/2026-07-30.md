### Design

**A real finding, not an assumption.** `hibernate-spatial:7.4.1.Final`'s
POM declares a dependency on `org.geolatte:geolatte-geom:1.11` — not JTS
(`org.locationtech.jts`), which is what most Hibernate Spatial examples
and tutorials online assume. Rather than adopt an entity-mapping
dependency with no verified precedent in this project's stack (and a
different geometry library than expected), decided to keep `location`
entirely unmapped on `CommunityResource` and do every geospatial read/
write through native SQL — documented as a deliberate choice, not a
workaround, in
[ADR-012](../decisions/ADR-012-postgis-nearby-search-design.md). This
also sidesteps the question entirely for nearby search, which always
needed a native `ST_DWithin`/`ST_Distance` query regardless (no JPQL
equivalent exists).

Also decided in ADR-012: `geography(Point, 4326)` over `geometry`
(spheroid-correct distance with no projection to choose), a single
native projection query for nearby search rather than a two-stage
ID-then-entity fetch (the latter risks losing the distance order on the
second query), and a 5 km default / 50 km maximum radius scoped to
Halifax without restricting resource coordinates themselves to a bounding
box.

### A Genuine Test-Isolation Bug, Found and Fixed

The first draft of `findNearbyReturnsAResourceInsideTheRadiusOrderedByDistance`
asserted `page.getContent().get(0).getDistanceMeters()` was `> 0` with no
keyword scoping — it passed in isolation but failed once the full suite
ran, because `ResourceApiIntegrationTest`'s HTTP-driven tests (real
`TestRestTemplate` calls, which commit independently of this test's own
`@Transactional` rollback) had already persisted a resource at the exact
same Halifax Library coordinate used as the search origin, landing at
distance exactly `0.0` ahead of this test's own "near" resource. Fixed by
scoping the query with a keyword filter unique to the test (matching the
`marker`-based isolation pattern every other test in this codebase already
uses) rather than relying on `.get(0)` against an unscoped result set.

### A Stale Local Database Volume, Diagnosed and Fixed (With Confirmation)

Manual verification against the real `docker compose` database initially
failed with `FATAL: role "hfx_connect" does not exist`, despite `docker
exec psql -U hfx_connect` working fine moments earlier. Root cause: this
machine's own native (non-Docker) PostgreSQL process was still listening
on `127.0.0.1:5432` (the same recurring port conflict documented in
`backend/README.md` from earlier milestones), so the Spring Boot app's
`localhost:5432` connection was silently reaching the wrong Postgres
entirely. Asked before taking the destructive step (recreating the local
`hfx_connect_postgres_data` Docker volume, which had also been left in a
stale, differently-initialized state from an earlier session) — user
confirmed proceeding — then resolved with the already-documented
`POSTGRES_PORT=55432`/`DB_PORT=55432` override.
